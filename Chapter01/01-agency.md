# درس 01 — You Have Agency
## اختیار عمل داری

## ایده اصلی

یکی از پایه‌های اصلی نگاه پراگماتیک این است که خودت را کاملاً منفعل نبینی.

اگر محیط کار، پروژه، مهارت‌ها یا روش انجام کار مشکل دارد، سؤال فقط این نیست:

> «چه کسی مقصر است؟»

سؤال بهتر این است:

> «در محدوده اختیار من، چه کاری می‌توانم انجام بدهم؟»

Agency یعنی مسئولیت حرفه‌ای خودت را بپذیری و منتظر نمانی همه‌چیز از بیرون اصلاح شود.

---

## مثال در پروژه React

فرض کن وارد پروژه‌ای می‌شوی و این Component را می‌بینی:

```tsx
const UserProfile = () => {
  // 600 lines...
};
```

داخل آن همه‌چیز وجود دارد:

- API Call
- Validation
- UI
- Business Logic
- State Management

واکنش منفعل:

> «پروژه از اول همین‌طوری بوده.»

واکنش پراگماتیک:

> «چه چیزی در محدوده کاری من است که بتوانم بدون ایجاد ریسک بهترش کنم؟»

مثلاً Data Fetching را جدا می‌کنی:

```ts
export async function getUser(): Promise<User> {
  const response = await fetch("/api/user");

  if (!response.ok) {
    throw new Error("Failed to fetch user");
  }

  return response.json();
}
```

---

## Agency یعنی همه مشکلات مال تو نیست

فرض کن API هشت ثانیه طول می‌کشد.

نباید بگویی:

> «Backend کنده، به من ربطی ندارد.»

ولی قرار هم نیست Backend را خودت بازنویسی کنی.

می‌توانی بررسی کنی:

- Loading State مناسب داریم؟
- Cache ممکن است کمک کند؟
- Pagination لازم است؟
- تمام داده‌های API لازم‌اند؟
- UX هنگام انتظار مناسب است؟
- Evidence کافی برای مطرح کردن مشکل با Backend داریم؟

پس:

```text
Responsibility ≠ Everything is your fault
```

بلکه:

```text
Responsibility =
ببین در محدوده اختیارت چه کاری می‌توانی انجام بدهی.
```

## مدل ذهنی

```text
مشکل
 ↓
چه چیزی در کنترل من است؟
 ↓
چه اقدامی کم‌ریسک و مفید می‌توانم انجام بدهم؟
 ↓
اگر خارج از اختیار من است، چطور آن را درست منتقل کنم؟
```

---

## نکته مهم

Agency به معنی این نیست که:

- بدون هماهنگی Architecture را عوض کنی.
- مسئول همه مشکلات پروژه شوی.
- Scope تسک را بی‌دلیل بزرگ کنی.

Agency یعنی منفعل نباشی و برای بخش قابل‌کنترل مسئله اقدام کنی.

---

## تمرین

یک پروژه React را در نظر بگیر که Component اصلی آن ۱۲۰۰ خط است.

Feature جدیدی داری که فقط بخشی از آن Component را درگیر می‌کند.

از خودت بپرس:

1. دقیقاً کدام بخش در Scope من است؟
2. چه چیزی را می‌توانم تمیزتر کنم؟
3. چه چیزی فعلاً نباید Refactor شود؟
4. چه ریسکی ممکن است با تغییر من ایجاد شود؟
