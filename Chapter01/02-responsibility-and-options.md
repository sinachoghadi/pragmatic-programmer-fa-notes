# درس 02 — Take Responsibility
## گزینه ارائه بده، نه بهانه

یکی از اصول مهم برنامه‌نویس پراگماتیک:

> Provide Options, Don’t Make Lame Excuses

وقتی مسئله‌ای پیش می‌آید، فقط توضیح نده چرا انجام نشد.

سعی کن همراه مشکل، راه‌حل یا گزینه ارائه بدهی.

---

## مثال

Feature باید امروز تحویل داده شود، اما API آماده نیست.

### پاسخ ضعیف

> Feature آماده نشد چون Backend API رو نداد.

ممکن است کاملاً درست باشد، ولی کمکی به تصمیم‌گیری نمی‌کند.

### پاسخ حرفه‌ای

> API اصلی هنوز آماده نیست. سه گزینه داریم:
>
> 1. UI را با Mock Data ادامه بدهیم.
> 2. Feature را پشت Feature Flag قرار دهیم.
> 3. انتشار این بخش را تا آماده شدن API عقب بیندازیم.
>
> پیشنهاد من گزینه دوم است چون Release بقیه قسمت‌ها را متوقف نمی‌کند.

---

## مثال TypeScript

فرض کن قرارداد API این است:

```ts
type PaymentStatus =
  | "pending"
  | "success"
  | "failed";
```

ولی Backend مقدار جدید می‌فرستد:

```json
{
  "status": "processing"
}
```

واکنش ضعیف:

> Backend قرارداد را خراب کرده.

این ممکن است درست باشد، ولی کافی نیست.

سؤال بهتر:

> سیستم Frontend من چطور می‌تواند در Boundary ورودی مقاوم‌تر باشد؟

مثلاً با Zod:

```ts
import { z } from "zod";

const PaymentSchema = z.object({
  status: z.enum([
    "pending",
    "processing",
    "success",
    "failed",
  ]),
});

type Payment = z.infer<typeof PaymentSchema>;
```

## تفاوت Engineer و Task Executor

Task Executor:

> نمی‌شود.

Engineer:

> با Scope فعلی سه راه داریم...

Task Executor:

> Backend آماده نکرد.

Engineer:

> Backend هنوز آماده نیست. برای متوقف نشدن Release می‌توانیم...

---

## نکته مهم

مسئولیت‌پذیری یعنی:

- اشتباه خودت را بپذیری.
- دیگران را بی‌دلیل مقصر نکنی.
- Problem را پنهان نکنی.
- گزینه بدهی.
- Risk را توضیح بدهی.

---

## تمرین

Feature دو روز عقب افتاده است:

- API یک روز دیر آمده.
- Estimation تو هم اشتباه بوده.
- Feature حدود ۹۰٪ آماده است.

یک پاسخ حرفه‌ای برای مدیر بنویس که شامل این موارد باشد:

1. وضعیت
2. علت
3. سهم خودت
4. گزینه
5. پیشنهاد
